# TicketRush — 기술 의사결정 로그

프로젝트: 콘서트 좌석 예매 시스템 (스탠딩+지정석 혼합, 선착순 오픈)
기간: 2026-08-10 ~ 2026-09-09 (30일, 1인 개발)

이 문서는 코드를 짤 때 참고할 아키텍처 결정과 그 근거를 기록한다.
"무엇을 만드는가"는 기획서를 참고하고, 여기는 "왜 이렇게 만들기로 했는가"만 다룬다.

## 1. 좌석 동시성 제어

- 스탠딩(수량제): Redis 카운터 `DECR`/`INCR`, 락 없음
  → Redis는 싱글 스레드라 단일 명령 자체가 원자적. 별도 락이 불필요함.
- 지정석(개별 좌석): Lua 스크립트로 `AVAILABLE → HELD` 원자 전이, 다중좌석 동시선택 시에만 그룹 단위 락 필요
  → 단일 좌석은 락 없이 처리하고, 여러 좌석을 묶어 선점할 때만 그룹 단위 락이 필요하기 때문에 범위를 최소화. 락 기술 자체(Redisson RLock vs DB 락)는 2번 벤치마크로 확정하며, 현재는 Redisson RLock을 1차 후보로 둔다 — 단일 좌석 흐름(Lua 스크립트, 락 불필요)은 이 결정과 무관하게 먼저 구현 가능.
  → **구현 단계에서 단순화**: 단일 좌석의 `AVAILABLE → HELD` 전이는 실제로는 Lua 스크립트가 아니라 `HSETNX`(필드가 없을 때만 값을 쓰는 단일 명령)로 구현했다. Redis 싱글 스레드 특성상 `HSETNX` 자체가 이미 원자적이라 "이미 HELD면 실패"를 보장하는 데 Lua가 필요 없었기 때문 — 동일한 원자성 보장을 더 단순한 방식으로 얻은 것이라 이 결정의 취지와 다르지 않다.
- 두 모델을 하나로 통합하지 않음
  → 카운터형과 개별자원형은 성격이 달라, 억지로 통합하면 오히려 로직이 복잡해짐.

### 사재기 방지 정책 (그룹 홀드 유지 전제)

- **계정당 이벤트별로 동시에 진행 중인 예약 시도는 1건만 허용한다.** 좌석(또는 스탠딩)을 홀드해놓은 상태에서 별도의 새 홀드를 또 시도하면 거절된다(`ACTIVE_RESERVATION_EXISTS`). 단, 이 규칙이 막는 건 "별도의 두 번째 시도"이지 "한 시도 안에 여러 좌석을 묶는 것"이 아니다 — 그룹 홀드(아래)는 여전히 1건으로 취급되어 허용된다.
  → 사재기 방지 목적. 이 규칙 덕분에 분산락(2번)이 필요한 그룹 홀드 기능 자체는 그대로 유지된다 — "1인 1매"를 좌석 개수 제한으로 해석했다면 그룹 홀드가 무의미해져 분산락 벤치마크(2번)가 통째로 필요 없어졌을 것.
- **한 건의 예약(그룹 홀드 포함)에 담을 수 있는 좌석/수량은 최대 2매다.** "동시 진행 1건 제한"은 병렬 시도만 막을 뿐 매수 자체를 제한하지 않으므로, 실질적인 사재기 방지는 이 상한이 담당한다.
- **한 계정이 한 이벤트에서 구매 확정(`PAYMENT_CONFIRMED`)할 수 있는 누적 매수도 최대 2매다** (시도당 상한이 아니라 이벤트 전체 누적 상한 — 일반적인 티켓팅 사이트 정책과 동일, 사용자 확인 완료). 한 번에 2매를 다 사면 그 이벤트에 대해서는 더 이상 구매 시도 자체가 막힌다.
- 몇 매를 살지 사전에 선언받는 화면/API는 두지 않는다 — 실제 매수는 홀드 요청에 담긴 좌석/수량 개수로 그때그때 정해지고(2매 상한 안에서 자유), 사전 선언은 순수 프론트엔드 안내(대기 화면 등)로만 처리한다.

### Redis 장애 시 홀드 상태 복구 전략

- `HELD` 상태(진행 중인 좌석 홀드)는 영속화하지 않는다.
  → `HELD`는 원래 TTL 5~10분짜리 임시 상태라, Redis 장애로 유실돼도 "그 순간 좌석 고르던 소수 사용자가 다시 골라야 하는" 정도의 영향으로 끝남.
  → 반면 `CONFIRMED`(결제 완료)는 이미 Outbox 패턴(6번)으로 DB에 원자적으로 저장되니 Redis가 죽어도 안전함.
  → 부수 효과: 이 설계 덕분에 Redis 자체의 영속성 옵션(AOF/RDB)을 고민할 필요가 거의 없다 — 어차피 `HELD`는 버려도 되는 상태이기 때문.
- Redis 재시작 시 필요한 건 "홀드 복구"가 아니라 "좌석 가용 수량 재구성"이다: `standing:remaining`과 좌석 상태를 DB 기준으로 다시 계산해서 채워 넣는 리컨실리에이션(rebuild) 잡을 실행한다.
- **rebuild 트리거**: 앱 기동 시 1회 + Redis 클라이언트의 재연결 이벤트 리스너가 재연결을 감지할 때마다. 단, "재연결"과 "데이터 유실"은 다른 개념이다 — 순간적인 네트워크 끊김으로 재연결됐을 뿐 Redis 데이터는 멀쩡한 경우까지 매번 rebuild를 돌리면 하필 트래픽이 몰리는 순간에 불필요한 부하가 걸릴 수 있다. 그래서 rebuild 완료 시 남겨두는 마커 키(`system:rebuild_epoch`)의 존재 여부로 먼저 판별한다: 마커가 살아있으면 데이터가 안전하다는 뜻이므로 rebuild를 스킵하고, 없으면(진짜 데이터 유실) 그때만 실행한다. rebuild가 성공적으로 끝나면(RENAME 완료 직후) 마커를 다시 세팅한다 — 이 사이에 크래시가 나도 마커가 없는 상태로 남을 뿐이라, 다음 기동 시 불필요하지만 안전한 rebuild가 한 번 더 실행되는 정도의 영향만 있다. 다중 인스턴스 환경에서는 재연결 이벤트가 여러 인스턴스에서 동시에 발생할 수 있으므로, 실행 자체는 분산락으로 단일 인스턴스만 수행하도록 가드한다. 이 가드는 2번에서 채택되는 락 기술을 구현 편의상 재사용할 뿐, 2번의 채택 기준(오버셀 0건 전제, 처리량 20%, 에러율 5%p)은 여기 적용되지 않는다 — 리빌드 가드는 저빈도(기동/재연결 시에만) 실행이라 정합성은 "정확히 한 인스턴스만 실행"이면 충분하고 성능 비교 대상이 아니다.
- **rebuild 적용 방식**: 새 키셋에 재구성을 다 채운 뒤 `RENAME`으로 한 번에 교체하는 원자적 스왑을 쓴다. 이를 위해 좌석 상태는 개별 좌석마다 키를 따로 두지 않고 이벤트 단위 자료구조(예: Hash) 하나로 묶어, RENAME 한 번으로 전체를 교체할 수 있게 설계한다 (db-schema.md의 Redis 키 설계에 반영할 것). **`standing:remaining`도 좌석 상태와 동일하게 이 rebuild 트리거·`rebuild:in_progress` 플래그·원자적 스왑 보호 대상에 포함된다** — 별도로 재계산 후 단순 `SET`하는 경로를 두면 좌석에서 막은 것과 같은 빈 키 문제가 스탠딩에는 그대로 남는다. 좌석 Hash에 통합할지 별도 키로 스왑할지는 db-schema.md의 Redis 키 설계에서 정한다. 단, RENAME이 원자적으로 보장하는 건 "교체되는 순간"뿐이다 — 데이터 유실이 확인된 시점부터 RENAME 전까지는 대상 키 자체가 존재하지 않는 구간이 생기며, 이 구간의 요청 처리는 아래 항목에서 별도로 다룬다.
- **rebuild 중 요청 처리 (빈 키 문제)**: rebuild를 시작하는 즉시(DB에서 채우기 전) `rebuild:in_progress` 플래그를 세팅한다. 좌석 조회/홀드 API가 대상 키를 찾지 못하면: 플래그가 켜져 있으면 "일시적으로 이용 불가, 잠시 후 재시도"로 응답하고(매진과 구분되는 별도 상태 — 실제로는 재고가 남아있는데 매진으로 오인시켜 이탈시키지 않기 위함), 플래그 없이 키만 없으면 정상 상황이 아니므로 에러 처리 + 알림한다(lazy 초기화로 조용히 채워 넣지 않음 — 이 경로 자체가 오버셀로 이어질 수 있어 원천 차단). RENAME 완료 후 플래그는 해제한다(안전장치로 짧은 TTL도 병행). **플래그 스코프(전역 vs `rebuild:in_progress:{eventId}` 등 이벤트 단위)는 지금 정하지 않고, 좌석 상태 키 네임스페이스를 정하는 구현 단계(13번의 "좌석 상태 모델")에서 함께 확정한다** — 이벤트별로 rebuild가 독립적이라면 전역 플래그는 무관한 다른 콘서트 조회까지 막는 부작용이 있다.
- **rebuild 시 "점유 중"으로 간주할 상태는 `CONFIRMED`뿐 아니라 `PAYMENT_REQUESTED`(아직 TTL 안 지난 것)도 포함해야 한다.** `CONFIRMED`만 기준으로 잡으면, 장애 시점에 결제 진행 중이던 좌석이 `AVAILABLE`로 풀려 다른 사용자에게 재판매되고, 이후 원래 결제의 PG 웹훅이 성공 처리되면서 동일 좌석에 대해 두 건의 `CONFIRMED` 예약이 생기는 오버셀이 재현될 수 있다. 여기서 "TTL 안 지남"의 기준값은 5번의 홀드 TTL(요청 멱등성 TTL과 동일)을 그대로 쓴다.

→ 카오스 테스트(8번)의 "정상 동작" 기준: "Redis 장애 중이던 홀드는 유실될 수 있으나(알려진 한계), 결제 진행 중이던 좌석과 확정된 좌석은 재시작 후 DB 기준으로 정확히 재구성되어 오버셀이 발생하지 않는다."

## 2. 분산락 방식 비교

- 이 벤치마크가 결정하는 것은 **다중좌석 동시선택(그룹 홀드) 시의 락 기술**이다. 단일 좌석 홀드는 Lua 스크립트로 락 없이 처리하므로 이 벤치마크 대상이 아니다(1번 참고).
- 대상: Redis(Redisson) vs DB 비관적 락(`SELECT ... FOR UPDATE`) — 두 방식을 실제로 구현하고 동일 조건(동일 Gatling 시나리오, 동일 인프라 스펙)에서 처리량/지연/에러율을 벤치마크 비교한다.
- 채택 기준: 오버셀 0건(정합성 검증 통과)을 최우선 전제조건으로 하고, 이를 만족하는 방식들 중에서만 처리량을 비교한다 — 정합성 없이 처리량만 높은 방식은 애초에 후보에서 제외한다. 정합성을 만족하는 방식들 사이에서는 처리량 차이가 20% 이내면 "유의미한 차이 없음"으로 보고 추가 인프라가 필요 없는 DB 락을 채택(운영 단순성 우선)하고, 20% 이상 차이나면 처리량이 높은 쪽을 채택한다. 락 획득 실패/타임아웃 에러율이 한쪽에서 뚜렷이(5%p 이상) 높으면 감점 요인으로 반영한다.
- Zookeeper는 후보에서 제외
  → ephemeral znode + ZAB 합의로 강한 일관성을 제공하지만, 3~5노드 앙상블 운영이 필요해 1개월 솔로 프로젝트에서 비용 대비 이득이 낮다고 판단.

## 3. 인증/인가 방식

- JWT 기반 (Access Token 단기만료 + Refresh Token), Role은 `BUYER` / `ORGANIZER` / `ADMIN`.
- 세션 대신 JWT를 택한 이유: 서버를 여러 인스턴스로 스케일아웃할 가능성을 고려해, 세션 클러스터링/스티키세션 없이 무상태로 인증을 처리하기 위함.
- **Refresh Token 저장/폐기 방식 (사용자 확인 완료)**: 클라이언트 전달은 httpOnly Cookie(Secure 속성 포함)로 한다 — Access Token과 달리 JS가 직접 다루지 않아도 되고, XSS로 탈취될 위험을 줄이기 위함. 서버는 Redis(`refresh_token:{accountId}`, redis-design.md 9번)에 발급값을 저장해두고, `/auth/refresh` 요청마다 클라이언트가 보낸 값과 대조해 검증한다 — 로그아웃/탈취 시 이 키를 `DEL`하면 즉시 무효화된다(무상태 JWT의 한계를 Redis 조회로 보완).
- **다중 기기 로그인은 지원하지 않는다(사용자 확인 완료)**: 계정당 Refresh Token을 1개만 유지한다(`refresh_token:{accountId}`, 계정 단위 키). 새로 로그인하면 기존 값을 덮어써 이전 기기의 Refresh Token은 자동 무효화되고, 그 기기는 이후 `/auth/refresh` 시도가 실패해 재로그인이 필요해진다. 기기/세션별 별도 토큰 관리(다중 기기 동시 로그인)는 범위 밖.

## 4. 대기열 (가상 대기실)

- Redis Sorted Set(`queue:{eventId}`, member=userId, score=진입시각)으로 순번 관리, `ZRANK`로 순번 조회
- Scheduler가 주기적으로 상위 N명에게 짧은 TTL의 입장 토큰 발급, 좌석 API는 이 토큰 검증 필수
- 입장 토큰 TTL = 좌석 홀드 TTL과 동일하게 설정. 단, 토큰은 대기열 통과 시점부터, 홀드는 좌석을 실제로 선택한 시점부터 각각 카운트가 시작되므로 시작점이 다르다 — 좌석 고르는 데 시간을 쓰면 홀드가 끝나기 전에 토큰이 먼저 만료될 수 있다.
- **좌석(또는 그룹) 홀드 성공 시점에 입장 토큰을 홀드 만료 시각에 맞춰 재발급(TTL 갱신)한다.** 이러면 토큰이 항상 현재 유효한 제약을 따라가서, 홀드는 멀쩡한데 토큰만 먼저 죽어 결제 시작 API가 막히는 상황을 방지한다. 이건 아래의 "방치 시 재발급 금지" 규칙과 트리거가 다르다 — 그 규칙은 아무 행동 없이 방치하다 만료된 경우를 막기 위한 것이고, 이건 실제로 홀드해 구매를 진행 중인 경우라 공정성 원칙과 충돌하지 않는다.
- 토큰이 실제로 만료됐다는 건 사용자가 오래 방치했다는 뜻이므로, **순번을 유지한 채 재발급하지 않고 대기열에 새로 진입**해야 한다(뒤로 밀림).
  → 이유: 순번 유지 재발급을 허용하면 "토큰만 쥐고 자리 비워두는" 방식으로 대기열 우회/독점이 가능해져 공정성 원칙과 충돌.
- **입장 토큰 검증 범위는 좌석 조회/선택/홀드 API에만 적용되고, 결제 확정 웹훅에는 적용되지 않는다.** 웹훅은 PG가 서버-to-서버로 호출하는 별도 채널이라 사용자 브라우저가 들고 있는 토큰과 무관해야 하며, 그 멱등성은 5번의 DB 상태 확인으로 별도 보장한다. (결제 승인 직전에 토큰이 만료돼서 정상 결제가 실패하는 상황을 방지하기 위한 명시.)
- Nginx Rate Limiting과는 역할이 다름 → Rate Limiting은 초과 요청을 순서 무관하게 거절하는 것이고, 대기열은 "먼저 온 사람이 먼저 산다"는 공정성을 보장하는 것. Nginx는 대기열 진입 API 앞단의 1차 방어로만 사용.
  → **구현 완료(2026-08-27, 자체 검증까지 마쳤으나 사용자가 직접 테스트 후 별도로 커밋할 예정 — 저장소에는 아직 반영 전)**: `nginx/nginx.conf` — `limit_req_zone`으로 `POST /events/{id}/queue/entries`만 제한(`~ ^/api/v1/events/[0-9]+/queue/entries$` 정규식이라 순번 폴링 `GET .../me`는 걸리지 않음)하고 나머지 API는 그대로 통과시킨다. rate=5r/s·burst=10은 홀드 TTL 등 다른 값들과 같은 성격의 placeholder — 3주차 Gatling 부하테스트에서 실측 후 조정한다. 로컬은 `docker-compose.yml`의 `nginx` 서비스(포트 8081)로 띄우고, 백엔드는 아직 컨테이너화 전이라 `host.docker.internal`로 호스트 프로세스를 가리킨다.
- 대기열 이탈(사용자가 탭을 닫거나 이탈하는 경우) 처리: 개별 사용자의 실시간 이탈 여부는 추정하지 않는다 — Rush 특성상 대기열이 예상보다 길어지는 것 자체가 정상 시나리오라, 시간 기준으로 오래 대기 중인 엔트리를 정리하면 실제로 기다리는 사용자를 오판해 쫓아낼 위험이 있다. 대신 매진되거나 이벤트가 종료된 시점에 대기열(`queue:{eventId}`) 전체를 일괄 만료시키는 것으로 단순화한다. 개별 이탈로 순번 계산이 다소 부정확해질 수 있으나 오버셀로 이어지지 않으므로 허용한다.
  → **구현 확인(2026-08-27)**: `EntryTokenScheduler`는 매 주기 고정 인원 수(`queue.admit-count`)만큼 뽑아 입장 토큰을 발급하고 즉시 대기열에서 제거하므로(`QueueRepository.remove`), 이탈자가 있어도 뒤쪽 순번이 밀리는 정체는 생기지 않는다(오버셀·무한대기 관점에서는 문제없음, 확인 완료). 다만 `admit-count`가 이탈률을 고려하지 않은 고정값이라, 한 배치에 이탈자가 많이 섞이면 그만큼 실사용자 입장 처리가 희석돼 체감 대기시간이 늘어날 수 있다는 점은 지금까지 검토된 적이 없었다 — **3주차 Gatling 부하테스트 시나리오에 이탈률을 섞은 케이스를 추가해 실측하기로 함(사용자 확인 완료)**. progress.md "시점이 정해진 결정" 참고.
- 봇 탐지/CAPTCHA, 멀티 리전 대기열 동기화는 범위 제외 (단일 Redis 인스턴스 기준)

## 5. 결제 정합성

- 요청 멱등성: Redis `SETNX` (TTL = 홀드 TTL과 동일)
- **`PAYMENT_REQUESTED` 상태는 결제 요청 API가 PG를 호출하기 직전에 `reservation` 행을 `requested_at` 타임스탬프와 함께 DB에 동기 INSERT한다.** `SETNX`로 요청 멱등성을 먼저 확보한 뒤(중복 요청 차단) 수행하므로 중복 행은 생기지 않는다. 이 행이 있어야 1번의 rebuild가 "TTL 안 지난 결제 진행 중" 좌석을 DB에서 조회해 점유 중으로 판단할 수 있다.
- **요청 멱등성의 2차 방어선으로 DB 유니크 제약을 쓴다.** Redis가 죽어 `SETNX` 키가 유실되면(정확히 8번에서 카오스 테스트로 검증하는 상황) 재시도 요청이 멱등성 체크를 그냥 통과해버려 PG를 중복 호출할 위험이 있다 — Redis 하나에만 의존하지 않기 위해, `reservation` 행에 대한 DB 유니크 제약을 두어 중복 INSERT 시도를 막는다. 스코프는 전역이 아니라 "진행 중인 시도"(`PAYMENT_REQUESTED`/`PAYMENT_CONFIRMED`)로 한정해야 한다 — 그렇지 않으면 취소/환불된 좌석의 재판매까지 막혀버린다. 구체적인 구현 방식(MySQL은 조건부 유니크 인덱스를 지원하지 않으므로 생성 컬럼 등으로 우회)은 db-schema.md에서 다룬다.
- 웹훅 멱등성: DB 상태 확인 (PG 웹훅 중복 수신 대비, 요청 멱등성과 별개로 이중 처리)
- 결제 실패/타임아웃 시 Saga 보상 트랜잭션으로 좌석 자동 반납
  - Choreography 방식 채택 (중앙 조율자 없음) → 이미 Kafka Consumer 기반 이벤트 구조를 쓰고 있어 별도 조율 컴포넌트 없이 자연스럽게 확장 가능하기 때문
  - 상태: `SEAT_HELD → PAYMENT_REQUESTED → PAYMENT_CONFIRMED` (정상) / `→ PAYMENT_FAILED → SEAT_RELEASED` (보상) / TTL 만료 시에도 동일 Consumer가 처리
- **예약/결제 테이블 구조: `reservation` 단일 테이블로 확정 (좌석 점유 + 결제 기록을 별도 테이블로 분리하는 안은 채택 안 함).** PG를 포트원 경유로 쓰기로 해 PG사 메타데이터 확장 부담이 적고, 상태 컬럼 하나로 Saga 상태머신을 단순하게 유지하는 쪽이 8번 카오스 테스트 검증에 유리하기 때문. (이후 그룹 홀드 지원을 위해 좌석 정보만 `reservation_seat` 자식 테이블로 별도 분리했지만, 이건 "결제 정보 분리"가 아니라 "한 예약에 좌석이 여러 개 담기는 것"을 표현하기 위한 것이라 이 결정과는 다른 축이다 — db-schema.md 5·6번 참고.)
- **PG사: 포트원 V2 경유로 토스페이먼츠(카드) + 카카오페이(간편결제) 2개 채널을 동시 지원하기로 확정(사용자 확인 완료, 1주차 웹훅 스모크테스트 진행 중 결정).** V2는 PG사와 무관하게 웹훅 페이로드/서명 검증 방식을 통일하므로, 채널이 2개여도 웹훅 수신·서명 검증·결제 확정 로직은 PG사별 분기 없이 하나로 처리한다. 결제 요청 시 프론트가 `channelKey`로 어느 채널을 쓸지만 선택하면 되고, 이 선택은 백엔드 결제 API에는 영향을 주지 않는다.
- **웹훅 서명 검증 방식(3주차 결제 연동, 가정 — 실서명 미검증)**: 1주차 스모크테스트 로그에 `webhook-signature` 헤더가 그대로 찍혔던 걸 근거로 [Standard Webhooks](https://www.standardwebhooks.com/) 스펙(`webhook-id`/`webhook-timestamp`/`webhook-signature` + HMAC-SHA256)을 따른다고 가정하고 구현했다. `PORTONE_WEBHOOK_SECRET`을 콘솔에서 아직 못 찾아 실제 서명으로 검증해본 적은 없음 — 발급받으면 재확인 필요(progress.md 추적). 시크릿이 비어있으면 모든 웹훅을 무조건 거절한다(빈 값 통과보다 안전).
- **웹훅 재검증 단순화(알려진 한계)**: 웹훅 body(`type`/`data.paymentId`)의 값을 그대로 신뢰해 결제 확정/실패를 판단한다. 원칙적으로는 포트원 결제 조회 API(GetPayment)로 서버 대 서버 재검증을 해야 하지만, 실제 결제 채널(카드/카카오페이) 프론트 SDK 연동이 아직 없어 검증할 대상 자체가 없다 — 프론트 PG 연동이 이어지는 시점에 함께 보강한다.
- **`pg_payment_id`의 실제 의미 정정**: db-schema.md에는 원래 "포트원이 발급하는 값"으로 적혀 있었으나, 실제 PortOne 연동 방식은 반대다 — **merchant(우리 서버)가 결제 요청 시점에 생성해 부여하는 식별자**(`"TICKETRUSH-{reservationId}"`)이고, 프론트가 포트원 SDK 호출 시 이 값을 그대로 넘긴다. 웹훅이 이 값을 담아 돌아오므로 이걸로 예약을 역조회한다(db-schema.md 5번에 반영 완료).

## 6. DB 쓰기 + Kafka 발행 원자성 (Outbox 패턴)

- DB 쓰기와 Kafka 이벤트 발행은 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없음
- 해결: DB 트랜잭션 안에 `outbox_events` 테이블도 함께 INSERT → Debezium이 이 테이블 변경을 감지해 Kafka로 발행
- Kafka 트랜잭션(exactly-once)은 결제확정 이후의 consume-transform-produce 구간(예: 정산 이벤트 발행)에만 적용 → DB-Kafka 간 원자성 자체를 Kafka 트랜잭션으로 오해하지 않도록 범위를 명확히 구분

**3주차 구현 범위 확정(2026-08-27, 사용자 확인 완료)**: outbox 이벤트는 **`PAYMENT_FAILED` 전이에서만** 기록한다(위 문단의 "결제확정 시" 표현은 이 확정 이전에 쓴 것이라 정정) — `markPaymentFailed`가 outbox에 `event_type=PAYMENT_FAILED`를 남기면, Kafka Consumer(`PaymentFailedConsumer`)가 이를 받아 보상 2단계(`releaseAfterFailure`, 좌석 반납)를 트리거한다. `PAYMENT_CONFIRMED` 이후의 정산/알림은 여전히 보류 중인 기능이라 outbox 이벤트를 만들지 않는다 — 그 기능이 생기면 같은 `outbox_events` 테이블에 `event_type=PAYMENT_CONFIRMED`로 추가하면 된다. 이 선택은 "정산" 같은 나중 기능의 자리표시자를 만드는 대신, 이 프로젝트 핵심(오버셀 없이 장애를 버티는가)과 직결된 실패 보상 경로에 Kafka exactly-once를 실제로 적용한 것이다.
- Kafka/Debezium은 at-least-once 전달만 보장하지만 `releaseAfterFailure`가 이미 상태 체크(`status == PAYMENT_FAILED`)로 멱등하므로 재전달돼도 안전하다 — "at-least-once + 멱등 소비자"로 exactly-once **효과**를 얻는다(진짜 Kafka 트랜잭션 API는 재발행 단계가 없는 이 소비자엔 적용하지 않음).
- **로컬 인프라 조정**: 이 파이프라인을 실제로 연결하는 과정에서 Debezium이 스키마 변경 이벤트를 `topic.prefix`와 같은 이름의 토픽에 발행하려다 `auto.create.topics.enable=false`(기존 설정) 때문에 무한 재시도에 빠지는 문제를 발견 — 커넥터 설정에 `include.schema.changes=false`를 추가하고, `docker-compose.yml`의 `KAFKA_AUTO_CREATE_TOPICS_ENABLE`을 `true`로 바꿔 해결(1인 로컬 개발 규모라 토픽 자동 생성 위험보다 이 문제를 피하는 실익이 큼). 커넥터 등록은 `scripts/register-outbox-connector.ps1`로 자동화했다. 상세 디버깅 과정은 portfolio.md 소재 5 참고.

## 7. Kafka의 역할 (오해 방지용 메모)

- DB 부하를 줄이는 주체는 Kafka가 아니라 Redis다. 좌석 선택 단계에서 대부분의 요청이 Redis 선에서 걸러지고, DB에는 좌석 홀드를 뚫고 결제 요청 단계까지 도달한 소수만 도달한다 (결제 확정 성공 여부와 무관 — 5번의 `PAYMENT_REQUESTED` INSERT부터 이미 DB에 닿는다).
- Kafka는 결제확정 DB 기록이 끝난 "이후"의 후속 작업(정산, 알림, 통계 등)을 사용자 응답과 분리시켜, 응답 속도를 지키고 부가 시스템 장애가 결제 자체에 전파되지 않게 막는 역할을 한다.

- 부하테스트(Gatling)로 처리량 검증 + 장애 주입 테스트로 정합성이 장애 상황에서도 유지되는지 검증 — "빠른가"뿐 아니라 "장애에도 안 깨지는가"까지 실측 증명하는 것이 이 프로젝트의 핵심 목표
- Redis 장애 시나리오의 정상 동작 기준은 1번 참고.
- Kafka 브로커 다운 시나리오의 정상 동작 기준: Kafka가 다운돼도 결제 확정(DB 트랜잭션 + outbox insert)은 정상적으로 완료되고 사용자 응답은 실패하지 않는다. 다만 Debezium이 outbox_events를 Kafka로 발행하지 못해 정산/알림 등 후속 이벤트는 브로커 복구 후 지연 처리되며, 그 사이 outbox_events 테이블에 미발행 레코드가 쌓일 뿐 유실은 없다. (이 기준은 수분~수십 분 내 복구되는 일시적 장애를 가정하며, MySQL binlog retention을 넘는 장기 장애는 범위 밖이다.)

## 9. 환불 정책

- MVP 범위: 전액 취소만 구현
  → Saga의 `PAYMENT_FAILED → SEAT_RELEASED` 보상 로직을 그대로 재사용할 수 있어 추가 구현 비용이 거의 없음
- 시점별 차등수수료, 부분환불은 구현 범위에서 제외 (설계 문서로만 남김)
  → 새로운 기술 개념 없이 비즈니스 룰과 케이스 수만 늘어나는 영역이라 판단

**구현 단계에서 정확히 확정(3주차)**: `POST /reservations/{id}/cancel`은 `PAYMENT_CONFIRMED` 상태에서만 허용하고(그 외 `RESERVATION_NOT_CANCELLABLE` 409), 도착 상태는 Saga 보상과 동일하게 `SEAT_RELEASED`를 재사용한다 — 여기까지는 "재사용"이 맞다. 다만 Redis 반납 로직은 `SeatService.compensate`(홀드 중 실패 롤백용, `hold`/`active_reservation`/`hold_schedule` 세 키를 함께 정리)를 그대로 쓰지 않고 **새 메서드 `releaseConfirmed`**를 추가해 썼다 — `PAYMENT_CONFIRMED`가 되는 순간 `confirmHold`가 이미 그 세 키를 전부 정리하고 `seat_status`만 "확정 판매"로 남겨두므로(redis-design.md 3번), 취소 시점엔 `seat_status`만 되돌리면 되고 나머지를 다시 건드리면 오히려 이미 없는 키를 지우는 무의미한 호출이 된다.

## 10. 인프라

- **확정: AWS EC2 + Docker Compose + RDS(MySQL). EKS/ElastiCache/MSK/CloudWatch는 도입하지 않는다(2026-08-27, 사용자 확인 완료).**
  → 신입 채용 포트폴리오 관점에서 "관리형 서비스를 써봤다" 자체는 변별력이 낮고, 오히려 채택 근거를 설명 못 하면 역효과가 난다. 이 프로젝트에서 실제로 강한 소재는 **분산락 두 방식을 직접 구현·실측해 근거를 갖고 선택한 것**(2번)이라, 인프라를 넓게 벌리는 대신 그 비교 결과를 정리하는 데 시간을 쓰기로 함.
  → Redis와 Kafka(Kafka Connect+Debezium 포함)도 로컬 `docker-compose.yml`과 동일하게 **EC2 위에서 Docker Compose로 그대로 운영**한다 — 별도 관리형 서비스로 옮기지 않음. MySQL만 RDS(관리형)를 쓰는 이유는 이미 원래 계획(1주차 이전)에 있던 결정이라 그대로 유지.
  → CloudWatch도 이번엔 별도로 구성하지 않는다(로그/모니터링은 범위 밖).

## 12. 이벤트/좌석 도메인 모델

- 콘서트(이벤트)는 여러 개 등록 가능하다 — `event` 엔티티가 존재하고, 좌석·예약·Redis 키(4번의 `queue:{eventId}` 등)는 모두 `event_id` 기준으로 스코프된다.
  → 이벤트가 1개든 여러 개든 Redis 키/DB 컬럼에 `event_id`를 넣는 비용은 거의 같다. 반면 이 프로젝트의 핵심 목표(8번: 오버셀 없이 폭주 트래픽을 버티는가)는 이벤트 개수와 무관하므로, 이벤트를 여러 개 지원한다고 해서 핵심 작업이 늘어나지 않는다.
- `ORGANIZER` 역할(3번)은 실제로 콘서트를 등록하는 기능을 가진다 — 역할만 정의되어 있고 실제 쓰임이 없는 상태를 피하기 위함.
- **`ORGANIZER` 가입은 `ADMIN` 승인이 필요하다.** 콘서트 등록 권한이라 아무나 가입 즉시 쓸 수 있게 두면 악용 위험이 있다. 가입 시 `account.status = PENDING`으로 시작하고, `ADMIN`이 승인해야 `ACTIVE`로 바뀌어 로그인이 가능해진다(db-schema.md `account` 테이블, api-design.md `ACCOUNT_PENDING` 에러 참고). `BUYER`는 이 절차가 없다. **`ADMIN` 역할의 첫 구체적 기능이 바로 이 승인 처리다** — 이전까지는 역할만 정의되고 실제 쓰임이 없었다.
- 좌석 배치는 자유 도형(좌석을 임의 위치에 배치하는 커스텀 에디터)이 아니라, **구역(등급) → 행 → 좌석번호의 사각 격자 구조**로 제한한다 (영화관 좌석 예매와 동일한 방식).
  → 자유 좌석맵 디자이너는 그 자체로 별도 제품 규모의 작업이라 1개월 솔로 프로젝트 범위를 벗어난다. 사각 격자는 이벤트 등록 시 "구역명 + 행 수 + 행당 좌석 수"만 입력받아 좌석을 자동 생성할 수 있어 구현 비용이 낮다.
- 구역마다 행 수·좌석 수가 다를 수 있다 (예: VIP 5행, R 10행). 스탠딩 구역은 격자를 두지 않고 잔여 수량만 관리한다 (1번과 동일한 모델).
- **구역명은 고정 목록이 아니다** — "VIP/R석/스탠딩"은 예시일 뿐이고, `ORGANIZER`가 원하는 이름으로 원하는 개수만큼 만든다. 따라서 구역 이름별로 정해진 상한 같은 것은 존재할 수 없다.

### 이벤트 규모 상한 (사용자 확인 완료)

- **이벤트 전체 좌석 수는 70,000석까지, 구역은 200개까지 허용한다.** (구역 수는 잠정값 — 3주차 부하 테스트에서 조정)
- **이벤트마다 다른 상한을 두지 않는 이유**: "이 공연은 3,000석"이라는 값은 상한이 아니라 주최자가 입력하는 값 그 자체다. 공연별 상한을 두려면 "이 공연은 몇 석까지 허용할지"를 미리 정해줄 주체가 필요한데, 결국 주최자가 신청한 숫자를 그대로 승인하게 되어 승인 단계만 늘어난다. 따라서 여기서 막으려는 것은 비즈니스 규칙이 아니라 **3,000석을 입력하려다 0을 더 눌러 300,000석을 보내는 실수나, 서버를 멈추게 하려는 악의적 요청**이다.
- **70,000이라는 값의 근거**: 국내 최대 공연장인 잠실올림픽주경기장이 약 69,000석이다. 실제로 존재하는 가장 큰 공연장을 여유 있게 담으면서, 자릿수를 잘못 입력한 값은 확실히 걸러지는 지점으로 잡았다.
- **구역 개수를 따로 제한하는 이유**: 좌석 총합만 막으면 "1석짜리 구역 70,000개" 같은 요청이 통과한다. 좌석은 `JdbcTemplate` 배치로 삽입하지만 구역은 JPA로 저장해 배치가 걸리지 않으므로, 구역 수만큼 INSERT가 낱개로 나간다.
- **구역 수 상한을 200으로 잡은 이유(잠정)**: 처음엔 50으로 뒀다가, 실제 공연장을 확인해보니 아레나급도 이미 50을 넘었다 — KSPO DOME(14,594석)은 1층만 43구역이고 플로어(B·C·D 블럭)와 2층까지 더하면 50을 초과한다. 여기서 **등급과 구역은 다른 개념**이라는 점이 중요하다: "R석"이라는 등급 하나가 여러 구역에 걸쳐 있고, 우리 모델의 `section`은 "가격 + 사각 격자" 단위라 물리적으로 떨어진 구역을 하나로 합칠 수 없다. 따라서 실제 구역 수만큼 등록해야 하므로 상한이 넉넉해야 한다. 좌석을 7만석(스타디움급)까지 허용하면서 구역만 50으로 막으면 앞뒤가 맞지 않는다. **정확한 값은 3주차 부하 테스트에서 조정하고, 지금은 현실적인 시나리오를 막지 않을 만큼만 열어둔다**(사용자 확인 완료 — 지금 단계에서 세밀하게 정할 필요가 없다고 판단).
- **검증은 반드시 `long`으로 계산한다**: `행 수 × 행당 좌석 수`를 `int`로 곱하면 오버플로가 나서(예: 50,000 × 50,000 = 25억 > `int` 최대값 21.5억) 음수나 작은 값이 되어 **오히려 상한 검사를 통과해버린다**. 구현 단계에서 확인한 함정.
- **`long`으로 바꾸는 것만으로는 부족하다 — 구역별로 먼저 검사한 뒤 합산해야 한다**: 구역 하나의 최대치가 `int` 최대값끼리의 곱인 약 460경이라, 이런 구역이 3개만 모이면 합계가 `long` 최대치(약 922경)를 넘어 같은 오버플로가 재현된다. 그래서 **구역 하나만으로 상한을 넘으면 합산 전에 즉시 거절**한다. 이러면 이후 합계는 최대 (구역 50개 × 70,000석)이라 넘칠 수 없다. "타입을 키우면 해결된다"가 아니라 **입력 범위를 먼저 좁혀야 안전해진다**는 사례.
- **검증 순서**: 규모 검증은 좌석을 만들기 전에 수행한다. 곱셈 자체는 나노초 단위라 비용이 없고, 느린 것은 좌석 INSERT다. 검증이 먼저 실패하면 DB에는 한 행도 쓰이지 않는다.

## 13. 구현 순서

인증/인가 기반 구축 → **ADMIN 승인(ORGANIZER 가입 승인 API, 12번)** → **이벤트/구역/좌석 등록 API(12번, api-design.md 2번)** → 대기열(순번 관리) → 좌석 상태 모델(단일 좌석 흐름) → 홀드 TTL/만료 처리 → Saga 상태머신 → 분산락 벤치마크(그룹 좌석 홀드 락 방식 확정) → Kafka exactly-once → 결제 연동(**예약 취소 API 포함**, 9번) → Nginx → 카오스 테스트 → 부하테스트 → AWS 배포

- **ADMIN 승인 → 이벤트 등록을 대기열보다 앞에 둔 이유(사용자 확인 완료)**: ADMIN 승인이 없으면 ORGANIZER 계정이 `PENDING`에 머물러 로그인 자체가 안 되고, 로그인이 안 되면 이벤트/구역/좌석 등록 API를 아무도 호출할 수 없다. 그리고 2주차 "좌석 상태 모델" 작업을 검증하려면 이벤트/좌석 데이터가 DB에 이미 있어야 하므로, 이 둘은 1주차 안에서 인증/인가 다음 순서로 먼저 끝나야 한다.
- **예약 취소 API를 별도 항목으로 분리하지 않은 이유(사용자 확인 완료)**: `PAYMENT_FAILED → SEAT_RELEASED` Saga 보상 로직(5번)을 그대로 재사용하므로 결제 연동 작업과 함께 진행한다.
