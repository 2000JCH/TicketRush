# 면접 예상 질문 노트

포트폴리오 본문에는 안 넣지만, 면접에서 그래프/표를 자세히 들여다보는 사람이 물어볼 수 있는 디테일을 모아둔다. `progress.md` 2026-09-12 "면접 대비" 계획과 연결.

## Q. 한계 테스트(4번 섹션) 그래프의 음영 박스 값이 표(P95/P99) 값이랑 안 맞아 보이는데?

**A.** 표 값은 그래프의 하늘색 음영 박스(annotation) 안에서 찍은 값이 아니라, **그 라운드(N)가 실제로 실행된 시간 범위 전체에서 `histogram_quantile`로 뽑은 최댓값**이다(`test-results.md` 453줄 기준). 박스는 그저 Gatling이 "대기열 진입" 요청을 동시 투입한 순간을 표시하는 마커일 뿐이다.

실제 흐름(`CapacitySimulation.java` + 서버 코드):
1. 박스 = N명이 동시에 `POST /queue/entries`(대기열 진입)를 쏘는 순간
2. 각 사용자는 `GET /queue/entries/me`(순번 폴링)를 **1초 간격**으로 최대 40회 반복
3. 서버 `EntryTokenScheduler`가 `queue.admit-interval-millis=1000`(1초)마다 배치로만 입장 처리 — N명이 한꺼번에 줄 서도 초당 소량씩만 입장
4. 입장한 사람만 좌석 조회 → 0.5~2초 랜덤 대기 → 그제서야 `POST /seats/holds`(그래프가 재는 요청) 발생

즉 좌석홀드 요청은 박스가 찍힌 순간이 아니라 "진입 → 1초 배치 입장 → 폴링 → 랜덤 대기"를 거친 뒤에 발생하므로, N이 클수록(=마지막 사람이 입장하기까지 오래 걸릴수록) 좌석홀드 요청들이 박스 구간을 넘어 다음 빈 구간까지 퍼져서 찍힌다 — 박스 끝난 직후 빈 공간에서 최고점이 나오는 이유. **측정 실수가 아니라 대기열 배치 입장 설계가 만드는 자연스러운 지연**이며, 표는 이 실제 실행 구간 전체를 기준으로 쿼리했으므로 정확하다.

## Q. 그럼 포트폴리오 이미지를 `capacity-limit/`(uri=All) 걸로 바꾸면 표랑 맞아떨어지나?

**A.** 아니다, 어떤 그래프를 쓰든(`load-test/` uri=좌석홀드든 `capacity-limit/` uri=All이든) 위 이유(요청 완료 시점 지연) 때문에 **박스 안의 값과 표 값은 애초에 정확히 겹쳐 보이지 않는다** — 이건 uri 필터 문제가 아니라 시계열 특성 문제다. 다만 **표 자체는 uri=좌석홀드 필터로 집계한 값**이므로, 숫자의 출처와 그래프의 범위를 맞추려면 `load-test/`(uri=좌석홀드)를 쓰는 게 맞다. `capacity-limit/`(uri=All)은 대기열 폴링 등 다른 API까지 섞여 있어 표 수치보다 항상 더 나쁘게(또는 다르게) 보이고, 이건 uri 범위 자체가 다르기 때문에 발생하는 별개의 불일치다.

**결론**: 그래프-표 미세 불일치(박스 vs 빈 공간)는 어느 이미지를 써도 생기는 정상적 현상이라 신경 쓸 필요 없고, uri 필터(좌석홀드 vs All)는 표와 같은 범위를 쓰기 위해 반드시 `load-test/`를 써야 하는 별개의 이유다.
